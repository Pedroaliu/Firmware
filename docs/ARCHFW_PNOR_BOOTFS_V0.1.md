# ArchFW PNOR, firmware VFS and BootFS direction v0.1

## Decision

ArchFW needs PNOR/flash storage and a firmware file namespace. It does not
need a POSIX-style general-purpose VFS in the microkernel.

The name **firmware VFS** means a stable namespace for boot objects and
service images. The first implementation is a small, read-only **BootFS / Image
Service** over PNOR partitions. Writable state is handled by separate journal,
NVRAM and variable services so immutable boot images and mutable state do not
share failure semantics.

## Hostboot source lessons

The Hostboot `release-fw1120` implementation separates PNOR section access
from its extended-image VFS:

- `PNOR::getSectionInfo()` exposes section location, size and security state;
- the VFS API provides module load, unload, existence, address and loaded-state
  queries;
- `VfsRp` obtains the `HB_EXT_CODE` PNOR section and consumes a module table at
  the start of the extended image;
- load/unload requests are sent to a VFS resource-provider message queue;
- module load establishes memory permissions and invokes module initialization;
- unload invokes finalization, removes access and releases mapped pages;
- page faults can pull pages from the PNOR-backed image;
- secure mode validates the section and can verify individual pages;
- a watcher detects a crashed VFS handler, records FFDC and restarts it.

ArchFW should retain the useful ideas—section abstraction, generated module
manifest, verified demand loading, resource-provider supervision and explicit
load/unload lifecycle—but not copy Hostboot's same-address-space module ABI.

## ArchFW service decomposition

```text
Boot0
  |
  | minimal manifest lookup and immutable verification
  v
PNOR Device Service
  |  raw read / erase / program / geometry
  v
Partition and Manifest Service
  |  SectionId/ObjectId -> extent, version, hash, policy
  v
BootFS / Image Service
  |  verify, decompress, relocate, instantiate
  v
Service Supervisor
  |  create AddressSpace/Thread/CSpace and grant capabilities
  v
Root Orchestrator / isolated hardware services / EDK II payload
```

The microkernel knows none of the following:

- flash partition formats;
- module names;
- signature formats;
- compression;
- rollback policy;
- filesystem paths;
- UEFI variables.

It only supplies MemoryRegion, AddressSpace, Thread, Capability, IPC, IRQ and
fault-routing mechanisms.

## Module lifecycle

ArchFW replaces direct C++ `init`/`fini` function pointers with a process-level
lifecycle:

```text
DISCOVERED
  -> VERIFIED
  -> MATERIALIZED
  -> ADDRESS_SPACE_CREATED
  -> CAPABILITIES_GRANTED
  -> STARTED
  -> READY
  -> QUIESCED
  -> STOPPED
  -> CAPABILITIES_REVOKED
  -> RELEASED
```

A service image cannot become runnable until its manifest, dependencies,
ownership role and capability set have been validated. Unload first quiesces
the service, then revokes derived capabilities, then destroys its address
space and memory objects.

## Initial image model

```text
PNOR / QEMU pflash0: immutable
+-- redundant manifest / TOC
+-- Boot0
+-- ArchFW kernel
+-- Root Orchestrator
+-- Platform IR
+-- service images
+-- EDK II payload
+-- recovery image

PNOR / QEMU pflash1: mutable
+-- UEFI variables
+-- boot and reconfiguration journal
+-- RAS recovery manifest cache
+-- update metadata
```

Each immutable object carries at least:

```text
ObjectId
ObjectType
FormatVersion
ObjectVersion
Generation
Offset
StoredSize
ExpandedSize
Alignment
HashAlgorithm + Hash
VerificationPolicy
CompressionType
LoadPolicy
EntrypointType
Dependencies
RequiredCapabilities
OwnershipRole
```

The manifest is generated by the build, never hand-maintained as C structures
and never parsed from CUE at runtime.

## QEMU staging

### M00

One flat kernel image is loaded with QEMU `-bios`. No PNOR parser is on the
CPU-entry critical path. This keeps reset, stack, trap and UART defects easy to
isolate.

### M00.4 / M01

Create a QEMU pflash image builder and a minimal read-only manifest parser.
Boot0 locates and verifies the kernel and Root Orchestrator from fixed object
IDs. Add corruption and stale-generation tests.

### M01 / M02

Move general module lookup and loading into an isolated BootFS / Image Service.
The Root Orchestrator receives only the capabilities required to instantiate
services. Add service restart and capability-revocation tests.

### M03

Attach a second pflash device for UEFI variables and persistent journals. Keep
all mutable state outside the immutable executable image.

## Explicit non-goals for the first implementation

- no POSIX pathname semantics;
- no directory mutation;
- no runtime package installation;
- no page cache inside the microkernel;
- no writable executable partition during normal boot;
- no shared writable mapping of executable modules;
- no driver loaded before the trust chain and ownership model are established.
